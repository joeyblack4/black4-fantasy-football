# Buzz as the common franchise interface

Inspected 2026-09-08. Read-only local source/artifact review; no franchise agents started, model requests, messages, credentials copied, Buzz changes, or production actions. The root audit separately ran initialize-only protocol probes, described below and in the companion evidence.

## Decision

Buzz can remain the one shared human conversation interface while each franchise keeps its company's native cognition runtime. Its ACP client accepts external commands, and Desktop supports user-defined ACP harness registrations. The registry is not a hard allowlist of model companies. Native ACP runtimes need scoped configuration and qualification; non-ACP native runtimes need protocol adapters. Neither case requires replacing native cognition with Goose or the Black4 OpenRouter loop.

The transport verdict is eight documented ACP routes (six native servers and two transport adapters preserving Codex/Claude cognition), one thin Muse MSP bridge to implement, and one unresolved ZCode native bridge where currently identified ACP projects are community implementations. One shared interface is achievable; all-ten feature parity is not yet proved.

The current implementation is not yet a complete, uniformly safe native-runtime interface. Model pinning can fail open, native permission requests are automatically allowed, native sessions are not restored after bridge restart, and native attachments are not forwarded. These are concrete integration gaps, not reasons to abandon Buzz.

## Required league adapter work

1. Preserve one Black4 interface: Buzz event -> durable league inbox -> selected native harness -> scoped Black4 tools/replies -> durable receipts. Prevent a second responder path for the same signing identity.
2. Register each runtime from a pinned manifest; materialize separate private workspace, native state/config roots and credential references. Process environment and filesystem access need enforcement outside prompts.
3. Make the handshake fail closed on wrong model, unknown identity, unsupported required tools, missing auth or unusable usage accounting. No fallback to the harness default.
4. Keep model-company and budget enforcement in Black4. Native subagents and ancillary summarizer/reviewer models must obey the same company rules.
5. Implement adapter session mapping, durable native IDs, restart recovery and cancellation reconciliation. Preserve uncertain writes instead of blind retries.
6. Provide an explicit scoped reply/action MCP surface. For each harness, prove one incoming event, one native turn, correct model evidence and one returned receipt in a synthetic league before considering activation.
7. Map Muse MSP and investigate ZCode app-server semantics. Implement attachment and human-approval parity only through supported capabilities, with unimplemented features shown unavailable.

Most of this can live in a league-local gateway or per-harness ACP wrapper: fail-closed model enforcement, scoped action/reply tools, usage reservation, native session mapping and Muse protocol translation do not inherently require a Buzz fork. A wrapper can restore a saved native session when Buzz requests a new logical session. Native approval requests can be blocked or handled by an explicit scoped approval tool outside the automatic ACP permission path. Showing native interactive approval cards directly in Buzz requires a real UI/broker integration; it cannot be claimed merely because ACP defines request_permission. Likewise, preserving rich attachment blocks directly through the current text-only Buzz ingress needs an ingress extension or an explicit file-reference tool workflow.

No production draft actions are authorized by this audit. Remaining unknowns are native authentication, exact model availability, shipped-build provenance, per-harness protocol qualification, usage reconciliation and deployment isolation.
