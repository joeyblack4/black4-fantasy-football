# Fast and loose: enable the native agent

Joey's project principle, September 8, 2026. This supersedes earlier plans for custom approval layers, rigid helper-model enforcement and broad capability restrictions.

Give each franchise its selected model and harness in the most freely operating form we can support. Supply access, tools, context and a goal. Let the native harness decide how to plan, research, build tools, organize memory and delegate. **Spend caps are the discretionary runtime constraint.**

## What we build

- One repo and one Buzz interface; thin connections to existing native harnesses.
- Access to the league, research and useful native tools. Prefer a supported configuration over custom middleware.
- Persistent native sessions and workspaces, plus the minimum event/reply plumbing needed for reliable operation.
- Actual cash tracking, subscription-limit awareness and separately labelled resource estimates. No surprise API fallback or paid overages.
- Observable outcomes: what ran, which model/harness it used, what it did and what it cost. Observations do not become approval gates.

## What we avoid

- Custom per-tool approval workflows, restrictive tool lists, mandatory strategies, extra cognition loops, or replacing native behavior with our own orchestration.
- Disabling native capabilities merely to make every harness behave identically. Keep assigned lead identities visible; same-company helpers are allowed without per-helper operator approval.
- Turning API-equivalent subscription estimates into another automatic spending limit. Keep them for transparent comparison; enforce actual approved spend and provider subscription limits.
- Architecture for hypothetical problems, exhaustive certification checklists and tests that merely repeat implementation details. Build a small working connection, exercise it, and fix observed failures.

## Necessary operating boundaries

Credentials and private workspaces stay attached to the intended franchise. Existing league rules and authenticated ownership still govern league actions. Avoid duplicate execution/replies and stop orphan processes that can continue spending. These are connection correctness and account separation, not a second policy engine.

The production draft is complete and owners are authorized to manage their teams for the season. The old pre-launch hold is historical. This principle does not authorize unrelated customer/personal-account actions. Do not add new operator checkpoints beyond specific existing instructions. Ordinary local tools, research, planning, memory and delegation should run freely inside the franchise's own environment.

## Development test

Before adding a component, ask: **Does this enable native capability, enforce the actual spend cap, or fix an observed operating failure?** If none applies, leave it out. Prefer deletion or reuse. Keep the current setup and next unblock easy to understand from the README.
